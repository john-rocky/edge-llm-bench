# T1c on LiteRT-LM 0.19.0 — Pixel 8a, N4 on the GPU with its caches kept (2026-11-05)

**Terms.** N4 = `Qwen3-4B_dynamic_wi4b32_afp32_gpu_composites.litertlm`, litert-community/Qwen3-4B at commit a45912eb (lfs sha256 `a11d1b4c…`, 2,272,915,968 B), the 4B file with int4 block-32 weights and GPU composite ops of the comparison in `results/raw/2026-10-29-t1c-qwen3-0190-p8a-android/` (added to the Hub repo on 2026-10-27). This dir is its third sitting on the Pixel 8a; the first two, and the phone's wheel, harness and protocol, are in that dir. A sitting is one stretch of time reserved on the shared phone (a hold). A GPU protocol process is one Python process that builds one GPU engine and calls `Benchmark(...)` 3 times (How). The memory guard is that dir's: it stops the process once MemAvailable reads under 400,000 kB on two polls 2 s apart, and the harness then reports exit 137.

**Question.** On 2026-11-03 a cold GPU protocol process finished one run and the guard then stopped it. Does a process that reads the weight and program caches of an earlier process get through?

**Answer.** Yes by the rule set before the run, but not every time. Three GPU protocol processes ran in one hold: A with no caches (it wrote them), then B and C reading A's. B ran its 3 runs under the guard (exit 0), its lowest MemAvailable 6,208 kB above the line. C, a second process reading the same caches and run only to add a process count, was stopped 39 s in, 13 s after its first session was created, with no run finished (exit 137). A also ran its 3 runs. The median of the two processes that ran is 104.6 / 8.74 tok/s prefill / decode, and the runs behind it do not agree: the decode figure moved about 40 % inside each process (below). The lowest MemAvailable was not higher in the processes that read the caches: 437,944 kB in A, 406,208 kB in B and 357,428 kB in C. In this sitting each process's lowest read fell within 43,000 kB of the guard's line, above it in A and B and below it in C.

**How.** `litert_lm.Benchmark(model, backend, prefill_tokens=1024, decode_tokens=256, max_num_tokens=2048)`, one engine, 3 runs per process, on the PyPI `litert-lm-api` 0.19.0 Android wheel on CPython 3.14.8 on the phone (`liblitert-lm.so` sha256 `28fa8433…`, `logs/p8a-2026-11-05/KIT_kpy_gpu_selftest_1.json`). Pixel 8a, Android 16, build CP1A.260505.005, one shared hold, ticket `t1c-p8a-4b-1105`, JST 15:31:07–15:47:50. Before each process the driver sent the phone to sleep (`KEYCODE_SLEEP`), force-stopped the background app packages (36, 28 and 22 of them) and ran `am kill-all`. The order and the rule for reading the result were written in the harness's notes before the first process started (those notes are not in this repo): B decides the question, and C runs only if B ran. The guard's line stayed as it was, no process was retried, and the phone did not reboot (`/proc/uptime` rose).

- Every process built its GPU engine with every node on the GPU (556/556, 556/556, 518/518 on `LITERT_CL`, the log's name for the OpenCL delegate). Each started through the harness's ready gate (it waits up to 300 s for Android's thermal status to be 0, none, or 1, light, and for every CPU policy's ceiling to be at its maximum), each at status 1. B and C waited 140 and 141 s for that. The GPU's clock was not read: the harness's probe reads Qualcomm's `kgsl` node, which this phone, with an Arm Mali GPU, does not have (`kgsl none` in the state lines).
- B and C read A's caches. Their stderr has the line `Initialized InferenceContext from serialized data` three times and A's has it zero times (every process's stderr also has `Initializing OpenCL-based API from serialized data` three times; that line is not the marker used here). The weight cache (2,011,150,872 B) and the program cache (5,043,000 B) kept their bytes and mtimes through B and C (`runlog.txt` lines 36, 43 and 50). From each process's START (the `R` field of its `.meta.json`) to the first `session_advanced.cc:76` line in its stderr took 51.4 s in A, 26.5 s in B and 26.2 s in C.
- C's stop line: `MEMGUARD: MemAvailable 358900 kB < 400000 at 1793861265: killed` (it carries the read that triggered the stop; the table's 357,428 kB is the lowest of the guard's 2 s reads). A and B did not stop; their lowest reads stayed 37,944 and 6,208 kB above the line.
- The runs do not agree within this repo's 5 % bar (spread-rule, `render_leaderboard.SPREAD_FLAG`). Inside a process the spread of the runs, as a share of the median, was 40.1 % (A) and 39.1 % (B) in decode and 5.6 % and 22.2 % in prefill. The third run's decode was 37.2 % (A) and 34.4 % (B) under the first's. A and B each ended at thermal status 2 (moderate) with the three CPU ceilings 44 %, 70 % and 70 % below their maxima (955 of 1,704, 712 of 2,367 and 880 of 2,914 MHz). C ended at status 1, its ceilings 22 %, 48 % and 35 % below. Which limit moved the decode figure was not read.
- The phone's swap counters (`/proc/vmstat`, whole phone), from the end of each clearing to the read right after the process, rose by 98,980 pages in and 377,604 out around A (227 s), 74,109 and 264,598 around B (336 s), 58,003 and 306,659 around C (214 s). How much of that paging was the process's own memory was not read.

**What this does not show.** Why A and B stayed above the line and C did not: the three started within 70,548 kB of each other. A run without the guard, a run with a smaller `max_num_tokens`, and the file now under `qwen3_4b_mixed_int4.litertlm` (lfs sha256 `4877b236…`, the same export with its weights moved out of the graph into a separate weights section of the file) were not tried here.

**Dashboard.** Nothing here is a run record in the repo's schema (`schema/result.v1.json`), so `results/summary` does not change. The Pixel 8a's Qwen3-4B rows stay out (`docs/dashboard-cells-v1.md`, "Per-device exclusion"). These numbers are not pooled with any other sitting.

**Files.** `RESULTS.md` (the harness's `summarize.py` on `logs/p8a-2026-11-05/`), `logs/p8a-2026-11-05/` (each leg's stderr, parsed JSON, meta and stdout for N4's three processes and the wheel's selftest; `runlog.txt`, the driver's log of the hold, with the clearing as counts, not package names; `device_props.txt`). A leg is one process's set of log files. The legs' logcat files are left out: they carry other processes' lines.
