# T1c on LiteRT-LM 0.19.0 — Pixel 8a column (2026-10-29; N4 sittings 2026-11-02 and 2026-11-03)

**Terms.** T1c = a lane (2026-10-15) that exported Qwen3-1.7B with int8 channelwise weights (`dynamic_wi8_afp32`) and Qwen3-4B with int4 block-32 weights (`dynamic_wi4b32_afp32`) through litert-torch's GPU-composite path (`--apply_gpu_composites=True`) and compared them with the Hugging Face files of the time. This dir is the Pixel 8a column of that comparison on the released LiteRT-LM 0.19.0; the Galaxy S26 column of the same day, with the same wheel, harness and labels, is `results/raw/2026-10-29-t1c-qwen3-0190-s26-android/`. The lane's own files (device scripts, plans, tables, round notes) are in a private lane repo; the lines this README relies on are restated here, with their lane-repo path where a line is cited. **Question.** Does N17 build its GPU engine on the Pixel 8a with LiteRT-LM 0.19.0, how fast is it against I17B, and does N4 run there? The phone ran the PyPI `litert-lm-api` 0.19.0 Android (aarch64) wheel on CPython 3.14.8 on the phone (`liblitert-lm.so` 22,656,360 B, sha256 `28fa8433…fc78`, `logs/p8a/KIT_kpy_gpu_selftest_1.json`), not this repo's Android build (the repo's pin moved to v0.19.0 on 2026-10-31, c22ebe61).

**Answer.** N17: yes. It built the OpenCL engine with every node on the GPU (436/436, 436/436, 406/406 for prefill_128, prefill_1024 and decode), answered the eight short questions 8/8, and was faster than I17B in the same hold: +199.5 % prefill / +64.6 % decode (GPU protocol, below). N4: no GPU rate. In both of its sittings its GPU engine was built with every node on the GPU (556/556, 556/556, 518/518) and the lane's memory guard (it stops the process once MemAvailable reads under 400,000 kB on two polls 2 s apart) stopped the process (exit 137): on 2026-11-02 2 s after the benchmark's session was created, on 2026-11-03, with background apps stopped first, after one finished run. One CPU process of 2026-11-03 ran its 3 runs under the same guard, median 16.7 / 4.89 tok/s prefill / decode, while the phone lowered its CPU clock ceilings 22–60 % by the end: not a number the dashboard would count under this repo's cpu-cap-rule (below).

**How.** One process per leg, `legpy.py` on the phone's CPython importing the wheel, as in the S26 column:

- protocol = `litert_lm.Benchmark(model, backend, prefill_tokens=1024, decode_tokens=256, max_num_tokens=2048)` (the class the `litert-lm benchmark` CLI runs), one engine, 3 runs; a process's figure = the median of its 3 runs; three processes A / B / C; the row = the median over A / B / C;
- dashboard prompt = `Engine(max_num_tokens=2048, enable_benchmark=True)`, per iteration a new conversation and `send_message(prompt, max_output_tokens=256)`, 2 iterations, with the 1K prompt of T1b's column (sha256 `f64fb515…`, 1,338 tokens);
- eight questions = `Engine(max_num_tokens=1280)`, a session with host-rendered ChatML and the bundle's sampler, one regex per question (GPU, N17 only);
- CPU protocol = the protocol on the CPU backend, one process per file.

**4B on this phone.** The lane's 2026-10-29 plan ran no 4B pair here (lane repo `qwen3_gpuopt_work/replace_0190_20261029/device/run_p8a.sh` line 4: "No 4B pair on this 8 GB phone"). It went by T1c's sixth round (2026-10-16) on a Developer Device Platform lab Pixel 8a (Android 15, LiteRT-LM main@b7c40ea81's `litert_lm_advanced_main`, T1c's own 4B export: N4's size, other bytes; lane repo `qwen3_gpuopt_work/exports_4b_17b_20261015/ROUND6.md` lines 33, 57 and 86): there the 4B GPU dashboard-prompt process built its engine, about 4 s into the first inference MemAvailable fell to 242,856 kB, and the guard stopped it (exit 137); by the plan's rule the compared file M4B was then not tried. This repo's dashboard has left the Pixel 8a's Qwen3-4B rows out since 2026-10-07 (`docs/dashboard-cells-v1.md`, "Per-device exclusion (2026-10-07)"). Neither record was this phone with this runtime and N4, so on 2026-11-02 N4 got one GPU protocol process here, with the same wheel, scripts and guard (MemAvailable under 400,000 kB on two reads 2 s apart → stop). MemAvailable was 2,773,368 kB at the start; the engine was built (556/556, 556/556, 518/518 on LITERT_CL, a 2,011,150,872 B weight cache written), the benchmark's session was created 42 s in, and at 44 s the guard stopped the process (exit 137, no run finished; the read on its stop line was 140,776 kB, and its lowest read over the 2 s polls was 0 kB, `MEMMIN` in the meta's `R` field). The phone did not reboot (uptime rose), and right after the stop MemAvailable read 3,849,092 kB. On 2026-11-03 N4 had a second sitting (hold `t1c-p8a-4b-1103`, `logs/p8a-2026-11-03/`) with three steps set before it started, in order, the next only when the one before it gave no 3-run process: (1) one cold GPU protocol process; (2) one CPU protocol process under the same guard (the lane's scripts put the guard on the 4B GPU legs only; the driver set it for this CPU leg too); (3) one GPU protocol process with the first process's weight and program caches kept. Before every N4 process the driver cleared memory: it put the screen to sleep, force-stopped every app package with a running process that was neither persistent (a process at `oom_score_adj` below 0) nor in the foreground (53 packages before the GPU process, 32 before the CPU process; the names are not in this dir) and ran `am kill-all`.

- GPU, step 1: MemAvailable read 3,612,308 kB after the clearing and 3,336,036 kB when the process started. The engine was built as on 2026-11-02 (the same node counts and weight cache size), the first run's session was created 41 s in, and that run finished: its stdout line reads prefill 106.2 / decode 9.59 tok/s, one run of a process the guard then stopped, not a rate. The second run's session was created at 77 s, and at 80 s the guard stopped the process (exit 137; the read on its stop line and its lowest read: 360,076 kB). MemAvailable read 4,178,036 kB right after.
- CPU, step 2: the process started at thermal status 0 with every CPU ceiling at its maximum and MemAvailable at 3,634,356 kB, and ran its 3 runs (exit 0; the guard's lowest read 1,300,640 kB): prefill 24.7 / 16.7 / 12.9, decode 5.46 / 4.60 / 4.89 tok/s, median 16.7 / 4.89. It ended at thermal status 1 with the three policies' ceilings 22 %, 55 % and 60 % below their maxima (1,328 of 1,704, 1,065 of 2,367 and 1,164 of 2,914 MHz). Between the end of the clearing and the read right after the process (`runlog.txt` lines 36 and 40, a window around the 367 s process) the phone's swap counters (`/proc/vmstat`, whole phone) rose by 1,310,737 pages in and 1,741,576 out; around the 80 s GPU process (lines 31 and 34) by 111,589 and 447,888. How much of that paging was the CPU process's own memory was not read. A sustained figure, not a headline, as the 2026-10-29 CPU rows.
- Step 3 did not run, because step 2 gave a 3-run process.

The phone did not reboot in either sitting (uptime rose). What these show: with the guard's 400,000 kB line, N4's GPU process on this phone was stopped within 3 s of a session being created, both times, the second time after one finished run; a GPU process with the caches kept, one without the guard and one with a smaller `max_num_tokens` were not tried. This dir has no N4 GPU rate and no M4B rate for the Pixel 8a.
