# T1b on LiteRT-LM v0.18.1 — Galaxy S26 column (2026-10-26)

**Terms.** T1b = a lane that pre-validated E2, a GPU-composite re-export of Qwen3-0.6B (litert-torch `--apply_gpu_composites=True`, not on Hugging Face), against OWN, the current Hugging Face file (`litert-community/Qwen3-0.6B`, `Qwen3-0.6B_dynamic_wi4b32_afp32.litertlm`), on LiteRT-LM main@b7c40ea81 (2026-10-14 and 15). The Hub PR = the pull request on Hugging Face that would replace OWN with E2. E2g / OWNg = metadata-only greedy copies of the two files for GSM8K; hold A = the first phone reservation of T1b's plan (speed, text, 8 questions, CPU, peak memory); the column = the Galaxy S26 rows of T1b's matrix. T1b's own files (`MATRIX.md`, `LANE.md`, `greedy/GREEDY.md`, the device scripts) are in a private lane repo; the lines this README relies on are restated here.

**Question.** Does the E2 re-export of Qwen3 0.6B (T1b, `litertlm-convert/qwen3_gpuopt_work`) build its GPU engine on the Galaxy S26 with the LiteRT-LM v0.18.1 Android kit? T1b's column on LiteRT-LM main@b7c40ea81 (2026-10-15, the same phone and OS build) did. The v0.18.0 kit did not (`unexpected type name 'float4'`), and v0.18.1 ships the same prebuilt GPU / OpenCL accelerator bytes as v0.18.0 (`libLiteRtGpuAccelerator.so` 75ee49f6…, `libLiteRtOpenClAccelerator.so` dfc714a0…).

**Answer: no.** E2's GPU engine fails at the OpenCL kernel build, as on v0.18.0: `delegate_opencl.cc:341] Failed to create litert::ml_drift::DelegateKernelLiteRt: UNKNOWN: Failed to build program executable - Build program failureBC-src-code:53:17: error: unexpected type name 'float4': expected expression` (`logs/s26/E2_gpu_dash_1.err`, exit 2, no BenchmarkInfo; the hold's driver flags NOGO_E2_GPU_s26 and skips E2's other GPU legs). The rest of hold A ran.

**How.** A copy of T1b's device scripts (`prevalidate_20261014/device`), changed only as in `t1b-copy.diff`: KIT = `external_weights_work/r6_3986_verify_0181/kit/v0181-bda62485` (tag v0.18.1 = bda624851 built with the WORKSPACE local fix; `kit/KIT.md` beside it), ADV_SHA, DDIR `t1b0181_qwen3_06b`, SUPERVISOR `bench-weekly-1026`, PLAN_S26 = hold A's 8 groups (no GSM8K: the greedy bundles E2g / OWNg are gone from T1b's dir, and the question is engine creation), OWN = the Hub blob of litert-community/Qwen3-0.6B (sha256 03e7da1e…, = T1b's OWN), the keeper's queue wait 12 h, DEV and `make_results.py`'s KIT_SUMS (re-pointed at the copy and at the v0.18.1 kit), and the results header. Shared S26 hold, ticket `t1b-qwen3-s26-0181`, 13:11:48–13:37:11 JST (1,523 s); the phone dir was removed at the end. The dashboard row uses T1b's copy of the 1K prompt (the text until 2026-10-19, before the repo's commit cc27f490; sha256 f64fb515…, 1,338 tokens), as T1b's column did. `RESULTS.md` was regenerated on 2026-10-27 from the same logs after that phrase of its header was corrected (it read "the text before 2026-10-20"); `t1b-copy.diff` shows the copy of that run, which differs from the 2026-10-26 copy that ran the legs only in that phrase.

- **Why the GSM8K cells are not run.** T1b reads GSM8K as the Hub PR's bar (T1b `LANE.md` §2 5: E2 within 4 points of OWN on each backend, and E2's GPU − CPU within 4 points of OWN's, in one sitting). With no E2 GPU cell the bar has no verdict on v0.18.1, and it is read again in the sitting of the release that would carry the Hub PR, so OWNg's GPU count and the two CPU counts would change no decision.
